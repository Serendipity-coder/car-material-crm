# 车材通 CRM 前端整体验证与后端实施要求

> 文档用途：统一记录当前前端实现进度、功能与权限验证结论，以及后端接入真实环境时必须完成的接口、权限、数据范围和业务一致性要求。
>
> 验证范围：车材通汽车维修/洗车/美容/汽配耗材渠道 CRM 前端。
>
> 验证日期：2026-11-13
>
> 明确边界：本项目当前只实现浏览器端前端，不实现后端服务、数据库、真实审计日志和服务端安全边界。文中所有“前端已实现”均指 Mock 或浏览器端演示能力，不代表真实生产环境已经具备安全性。

## 一、最终结论

当前前端已经具备较完整的 CRM 演示和业务操作闭环，能够在 Mock 模式下完成：角色创建和权限赋值、一个用户绑定多个角色、多角色权限合并、不同角色显示不同页面和操作、不同部门隔离业务数据、管理员查看全量数据，以及线索、客户、报价、订单、发货、回款、售后和待办之间的主要数据流转。

整体评估为：**前端功能链路基本完整，RBAC 和部门数据隔离在 Mock 场景下可用；切换真实 API 后，后端必须重新执行最终身份认证、权限校验、数据范围过滤、敏感字段脱敏、并发控制和审计记录。尤其是“本部门及下级”和品类级数据范围，不能只依赖前端过滤。**

本项目明确不把“系统设置功能不完整”作为本阶段前端验收阻塞项。员工管理、部门管理、角色管理和角色内权限目录已实现；基础配置、真实操作日志等属于后续后端和产品范围，不在本阶段承诺为完整能力。

## 二、技术与运行边界

- 技术栈：Vue 3.5、Vite 6、TypeScript 5.7、Element Plus 2.9、Pinia 2.3、Vue Router 4.5、ECharts 5.6、Axios、Day.js。
- Mock 模式由 `VITE_USE_MOCK` 控制，Mock 数据和操作结果保存在浏览器 `localStorage`。
- 真实模式由 `VITE_API_BASE_URL` 指向后端，前端通过可替换的 REST 资源接口访问服务端。
- Mock 种子数据已扩充为汽车维修、洗车、美容、轮胎、汽配门店和耗材渠道场景，种子迁移版本为 `4`。
- 已完成生产构建验证：

```text
vue-tsc --noEmit && vite build
✓ 2170 modules transformed
✓ built successfully
```

- Vite 仍提示部分打包 chunk 超过 500 kB，这是性能优化建议，不影响当前构建和功能运行。

## 三、前端已经实现的能力

### 3.1 工作台与业务模块

已覆盖以下导航和业务模块：

- 工作台：经营概览、我的待办；
- 客户管理：销售线索、客户公海、客户档案、联系人、跟进记录；
- 产品管理：产品分类、产品档案、客户价格；
- 销售管理：销售商机、报价单、销售订单、退换货单；
- 交付与回款：发货记录、收款记录、应收账款；
- 售后管理：售后工单、客户回访；
- 数据统计：销售统计、客户采购分析、产品销售分析；
- 系统设置：员工管理、部门管理、角色管理。

多数业务模块采用配置驱动的通用列表、筛选、分页、详情、表单和 CRUD 模式，同时对报价、订单、客户工作台、线索旅程、产品 SKU 等场景提供了专门交互。

### 3.2 客户和线索流转

前端已支持：

1. 销售线索记录客户主体、门店、联系人、地区、经营项目、采购品类、来源、意向和负责人；
2. 线索可以转化为正式客户；
3. 同名客户存在时关联既有客户，避免重复创建；
4. 转化时可同步创建联系人；
5. 线索有下次跟进日期时自动生成首次跟进待办；
6. 公海客户可认领，认领后写入负责人、状态和认领时间；
7. 客户工作区可以查看联系人、跟进、商机、订单和相关业务记录。

### 3.3 报价、订单和交付回款

前端已支持：

1. 报价明细包括产品、SKU、数量、单价、折扣、税费和运费；
2. 报价审批状态会保存到报价记录；
3. 已通过或已接受的报价可以转为销售订单；
4. 转单时继承客户、商机、联系人、门店、收货地址、付款条件、产品明细和价格信息；
5. 订单生成后会初始化发货状态和回款状态；
6. 订单完成后更新客户累计采购额、采购次数、最近订单和最近联系日期；
7. 订单完成或报价转单后可以自动生成回访、补货等待办；
8. 发货、签收、收款和应收数据用于展示订单履约和回款状态；
9. 应收账款支持应收、已收、未收、逾期和结清状态展示；
10. 退换货、售后工单和客户回访均有独立业务记录。

### 3.4 数据丰富度与行业适配

Mock 数据已替换为车材通行业数据，并增加了：

- 汽修厂、洗车中心、汽车美容店、轮胎服务店、汽配服务站和连锁维修中心；
- 机油、齿轮油、滤清器、洗车液、镀膜剂、雨刷、轮胎、刹车片、制动液、灯具和工具设备；
- 线索、客户、公海、联系人、跟进、商机、报价、订单、发货、收款、应收、售后和回访记录；
- 产品分类、SKU、产品明细、客户价格和报表数据；
- 工作台待办、回款提醒、报价到期提醒、客户补货提醒、售后提醒和低库存提醒。

已有浏览器缓存会根据种子版本迁移逻辑追加新增数据，不需要手动清空缓存。

## 四、权限与数据范围验证结果

### 4.1 认证会话

Mock 登录成功后会保存当前用户、令牌、部门、角色 ID 和权限编码。真实模式会从后端登录接口读取标准化会话信息。退出登录时会清理本地认证信息。

前端不应被视为最终认证边界。真实后端必须从 token 或 session 中解析用户身份，不能信任浏览器传入的用户 ID、角色 ID 或部门 ID。

### 4.2 角色创建和权限赋值

角色管理已支持：

- 创建角色；
- 编辑角色名称、标识、排序、状态和说明；
- 删除未被员工使用的角色；
- 启用或停用角色；
- 按目录、页面和操作节点为角色分配权限；
- 角色权限预览；
- 权限目录管理入口；
- 超级管理员角色保护。

角色权限以 `menuIds` 保存，登录时转换为权限编码集合。真实后端必须在保存角色权限时校验菜单节点是否存在、权限节点是否属于当前租户，以及操作人是否有角色授权权限。

### 4.3 一个用户绑定多个角色

员工的 `roleIds` 是数组，一个用户可以绑定多个启用角色。登录时会读取所有启用角色并按权限并集合并：只要任一角色有权限，用户就具备该权限。

前端示例：

```ts
roleIds: ['r2', 'r4']
```

员工管理已支持在新增和编辑员工时选择多个角色，并维护角色成员数量。停用角色后，该角色不再参与新会话的权限合并。

真实后端必须在每次登录、刷新 token、访问接口和执行写操作时重新计算或校验有效角色，不能只依赖前端登录时保存的权限快照。

### 4.4 页面级和操作级权限

路由使用 `meta.permission` 做页面访问拦截，没有权限会进入 403 页面。页面按钮和操作使用 `v-permission` 或 `auth.can()` 控制显示和执行。

已覆盖的权限类型包括：

- 列表查看；
- 新增；
- 编辑；
- 删除；
- 导出；
- 审批；
- 认领和分配；
- 线索转客户；
- 报价转订单；
- 订单履约；
- 角色授权；
- 员工、部门和角色维护。

前端隐藏按钮只能改善用户体验，后端必须对每个接口再次校验同一权限。

### 4.5 不同部门看到不同业务数据

Mock API 会根据当前用户所属 `departmentId` 给部门业务资源附加部门过滤。当前已覆盖：

- 线索、公海、客户、联系人、跟进；
- 产品分类、产品、客户价格；
- 商机、报价、订单、退换货；
- 发货、收款、应收；
- 售后工单、客户回访；
- 销售、客户采购和产品销售报表。

产品和产品分类按部门归属关联。创建或编辑产品时，前端 Mock API 会校验产品分类是否属于所选部门，避免跨部门挂载分类。

普通用户没有有效部门 ID 时，部门业务查询会失败关闭，不会退化为显示全部数据。

### 4.6 管理员全量访问

管理员角色使用 `*` 权限，或拥有 `system:data:all` 数据范围权限时，不附加部门过滤，可以查看全部产品和全部业务数据，并可以在工作台和列表中切换部门。

管理员保护规则包括：

- 超级管理员不能停用；
- 超级管理员不能删除；
- 不能移除最后一位启用状态的超级管理员；
- 管理员角色必须保留全部权限；
- 被角色使用的角色不能删除。

### 4.7 “我的待办”和经营概览口径

“我的待办”只显示当前用户作为负责人、协办人或创建人的待办。经营概览的待办卡片已统一使用相同的当前用户过滤规则，避免概览显示了他人任务、但进入“我的待办”找不到的问题。

## 五、真实后端必须完成的内容

以下内容是前端切换真实 API 前的后端必做项。前端 Mock 的结果不能代替这些能力。

### 5.1 认证与会话

建议提供或兼容以下接口：

| 接口 | 作用 | 后端要求 |
|---|---|---|
| `POST /api/v1/auth/login/code` | 登录 | 校验账号、密码、手机号、验证码，签发短期 access token |
| `POST /api/v1/auth/sms/send-code` | 登录验证码 | 限流、过期时间、错误次数和风控 |
| `POST /api/v1/auth/register/send-code` | 注册验证码 | 限流、防刷、手机号唯一性校验 |
| `POST /api/v1/auth/register` | 注册 | 校验密码策略、手机号唯一性和账号状态 |
| `GET /api/v1/auth/me` | 当前用户 | 根据 token 返回实时用户、角色、部门和权限 |
| `POST /api/v1/auth/logout` | 退出 | 作废 refresh token 或服务端会话 |
| `POST /api/v1/auth/password` | 修改密码 | 校验旧密码、密码复杂度和会话风险 |

返回的当前用户至少应包含：`id`、`name`、`account`、`departmentId`、`department`、`roleIds`、`roles`、`permissionCodes`。

建议使用短期 access token + refresh token，服务端保存 token 版本或会话撤销信息，确保员工停用、角色停用或权限变更后能够及时失效旧会话。

### 5.2 员工、部门和角色接口

当前前端已按以下资源进行适配：

| 接口 | 作用 |
|---|---|
| `GET /api/v1/system/users` | 员工分页、搜索、部门和角色筛选 |
| `GET /api/v1/system/users/{id}` | 员工详情 |
| `POST /api/v1/system/users` | 新增员工 |
| `PUT /api/v1/system/users/{id}` | 编辑员工及多角色绑定 |
| `PATCH /api/v1/system/users/status` | 批量启用/停用员工 |
| `GET /api/v1/system/users/summary` | 员工统计 |
| `GET /api/v1/system/depts/tree` | 部门树 |
| `POST /api/v1/system/depts` | 新增部门 |
| `PUT /api/v1/system/depts/{id}` | 编辑部门 |
| `DELETE /api/v1/system/depts/{id}` | 删除部门 |
| `GET /api/v1/system/roles` | 角色列表 |
| `GET /api/v1/system/roles/{id}` | 角色详情，必须包含完整权限节点 |
| `POST /api/v1/system/roles` | 新增角色 |
| `PUT /api/v1/system/roles/{id}` | 编辑角色 |
| `DELETE /api/v1/system/roles/{id}` | 删除角色 |
| `PUT /api/v1/system/roles/{id}/menus` | 保存角色权限 |
| `GET /api/v1/system/menus/tree` | 权限树 |

后端必须校验：

- 员工账号唯一；
- 员工至少绑定一个有效角色；
- 停用角色不能再分配给员工；
- 删除角色前必须确认没有员工使用；
- 删除部门前必须确认不存在下级部门和直属员工；
- 不能停用或删除最后一个启用超级管理员；
- 普通管理员不能给自己授予超出自身权限的角色授权能力；
- 角色权限节点必须属于当前系统和当前租户。

### 5.3 通用业务资源接口

前端通用模块使用以下资源名称，真实后端应提供分页列表、详情、创建、更新、删除和必要的状态操作：

```text
leads
pool
customers
contacts
followups
product-categories
products
customer-prices
opportunities
quotes
orders
returns
shipments
payments
receivables
service-tickets
visits
reports-sales
reports-customer-purchase
reports-product-sales
```

列表接口至少应支持：

- `pageNum`；
- `pageSize`；
- `keyword` 或 `search`；
- 资源自身筛选字段；
- `departmentId`；
- `sortBy`；
- `sortOrder`；
- 报表的 `startDate` 和 `endDate`。

分页返回建议统一为：

```json
{
  "rows": [],
  "total": 0
}
```

### 5.4 后端数据范围校验

后端必须根据 token 中的用户、角色和组织关系计算有效数据范围，至少支持：

- 仅本人；
- 本部门；
- 本部门及下级；
- 指定部门集合；
- 全部部门；
- 指定产品品类；
- 全部品类。

重要规则：

1. 普通用户传入其他 `departmentId` 时，后端必须忽略或拒绝，不能按客户端参数直接查询；
2. 普通用户创建业务记录时，后端必须将归属部门强制设置为当前授权部门；
3. 普通用户更新业务记录时，后端必须检查原记录是否在当前数据范围内；
4. 详情、关联下拉选项、导出、统计接口都必须使用同一数据范围；
5. 报表汇总必须在 SQL 查询或服务层按数据范围计算，不能先汇总全量再让前端隐藏；
6. 品类受限用户不能通过订单明细、报价明细、客户价格或导出接口间接拿到未授权品类；
7. 无部门归属且无全局权限的用户必须失败关闭，不得返回全量数据；
8. 本部门及下级必须由后端递归计算部门树，不能只依赖前端追加过滤。

### 5.5 业务字段和归属字段

所有需要隔离或审计的业务记录建议具备：

```text
id
createdAt
updatedAt
createdBy
updatedBy
departmentId
ownerId
ownerName
status
```

不同资源还应具备稳定的关联 ID，而不是只保存名称：

- 客户：`customerId`；
- 联系人：`contactId`；
- 线索：`leadId`；
- 商机：`opportunityId`；
- 报价：`quoteId` / `quoteNo`；
- 订单：`orderId` / `orderNo`；
- 产品：`productId` / `skuId`；
- 产品分类：`categoryId`；
- 发货和收款：`orderId`。

名称可以用于展示和兼容旧数据，但业务关联、权限判断、去重和状态同步必须使用稳定 ID。

### 5.6 业务事务和状态一致性

后端必须以事务或可靠消息保证以下操作的一致性：

#### 线索转客户

- 防止并发重复创建同名或同编码客户；
- 线索转化、客户创建、联系人创建和待办创建需要可追踪；
- 重复转化时返回既有客户，不重复生成客户。

#### 报价转订单

- 校验报价状态和有效期；
- 校验产品、价格、折扣、税费和库存规则；
- 生成订单时保留报价来源；
- 防止同一报价被并发转成多个订单；
- 订单明细应保存当时的价格快照，不能依赖产品当前价格反算历史订单。

#### 订单、发货、回款

- 发货记录和收款记录必须引用真实订单 ID；
- 订单履约状态应由发货明细和签收结果统一计算；
- 订单回款状态应由收款和退款记录统一计算；
- 应收账款余额、逾期天数和结清状态必须由服务端计算；
- 重复提交收款或发货请求必须具备幂等键。

#### 待办和提醒

- 自动生成的待办需要来源类型、来源 ID和幂等约束；
- 同一订单不能重复生成相同类型的回访和补货任务；
- 待办完成、取消和重新打开需要记录操作人和时间；
- 经营提醒应区分实时计算提醒和持久化待办。

### 5.7 敏感字段和导出安全

以下字段必须由后端根据权限脱敏或拒绝返回：

- 单价、底价、成本价；
- 报价金额、订单金额、收款金额、应收余额；
- 客户累计采购额和利润率；
- 联系电话、邮箱、收货地址；
- 账号、登录 IP 和其他个人信息。

导出接口必须重新执行权限和数据范围校验，不能因为前端按钮被隐藏就认为导出安全。建议后端提供专用导出接口并写入审计日志。

### 5.8 审计和操作日志

真实操作日志不属于当前前端完成范围，但后端必须为生产环境补齐。至少记录：

- 操作人、角色和部门；
- 请求时间、IP、设备和 trace ID；
- 资源、记录 ID和操作类型；
- 操作前后关键字段差异；
- 成功/失败和失败原因；
- 角色权限变更、员工停用、数据导出、价格查看、订单状态变化等高风险操作。

日志应支持按时间、操作人、资源、结果和关键字查询，并设置留存周期和防篡改策略。

## 六、前端当前限制和后端接入注意事项

1. `localStorage` 只适合 Mock 演示，不适合保存真实 token、密码、权限快照或敏感业务数据；
2. 前端数据过滤不构成安全边界，后端必须在 SQL、服务层和导出接口统一执行范围；
3. 前端能展示多角色并集，但角色变更后的实时失效必须由后端会话机制保证；
4. 前端可以计算部分金额和提醒，但正式账务、库存、回款和应收状态必须以后端为准；
5. 前端的浏览器端策略草稿只能作为界面辅助，不能替代服务端的角色数据范围配置；
6. 报表如果由后端直接聚合返回，后端必须保证聚合前已完成权限过滤；
7. 真正上线前需要用真实 API 进行跨部门、跨角色、并发和越权测试。

## 七、建议的后端验收用例

### 7.1 角色和多角色

- 创建“销售专员”角色，只授予线索和客户查看权限，确认不能访问订单页面；
- 给同一员工同时绑定“销售专员”和“客户成功”，确认两个角色权限合并；
- 停用其中一个角色，重新登录确认该角色权限消失；
- 尝试删除仍被员工使用的角色，后端应拒绝；
- 尝试停用最后一个超级管理员，后端应拒绝；
- 低权限管理员尝试给自己授予超级管理员菜单，后端应拒绝。

### 7.2 部门和数据范围

- 华东销售部用户只能查看华东数据；
- 华南销售部用户不能通过修改查询参数查看华东数据；
- 本部门及下级用户可查看下属部门数据；
- 无部门用户不能查看部门业务数据；
- 管理员可以查看所有部门产品、客户、订单和报表；
- 普通用户创建客户、线索、订单时，篡改部门参数不能改变后端归属。

### 7.3 品类和敏感字段

- 只允许查看“清洗美容”的用户不能查询“底盘制动”产品；
- 报价、订单、客户价格和导出接口不能泄露未授权品类；
- 无敏感金额权限的用户不能从详情、列表、报表或导出中获得金额；
- 管理员可以查看全量金额，但仍需记录高风险查看和导出日志。

### 7.4 数据流转和并发

- 同一线索并发转化不能创建两个客户；
- 同一报价并发转单不能创建两个订单；
- 同一收款请求重复提交不能重复入账；
- 发货、收款和退换货并发更新时，订单状态和应收余额最终一致；
- 自动待办重复触发时不能产生重复任务。

## 九、交付状态

当前前端可以作为：

- 车材通 CRM 产品原型；
- 业务流程演示系统；
- 后端接口联调前的 Mock 客户端；
- 角色、部门和数据范围交互验收客户端。

当前前端不能单独作为：

- 真实生产权限系统；
- 真实账务或库存系统；
- 真实审计系统；
- 多租户安全隔离系统；
- 后端数据一致性的唯一来源。

后端完成本文第五章的认证、RBAC、数据范围、业务事务、敏感字段、审计和并发能力后，再将 `VITE_USE_MOCK` 切换为真实模式并进行第七章验收用例测试。
